# Chalk Agent Adapter Protocol v1

**Protocol identifier:** `chalk-agent-adapter/1`
**Status:** proposed, normative foundation for milestone #5

This document defines the seam between Chalk Protocol and a program that invokes a coding agent.
It specifies role intent, transport, access, output, identity, usage, and failure behavior without
depending on a provider, model, or CLI. The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**,
and **MAY** are normative requirements.

## 1. Scope

Chalk owns project state and the gates that decide whether work advances. An adapter translates one
Chalk role request into a provider CLI invocation and translates the result back into the common
response envelope.

The protocol does not define provider authentication, model quality, model names, or provider CLI
flags. It is not a general-purpose agent framework and does not let an adapter mark Chalk work done.

## 2. Transport

A Protocol v1 adapter MUST be an executable command that:

1. receives exactly one UTF-8 JSON request object on standard input;
2. runs with its process working directory set to `request.workingDirectory`;
3. writes exactly one UTF-8 JSON response object to standard output; and
4. writes human-oriented process diagnostics, if any, to standard error.

Chalk MUST pass the request as process input, not interpolate it into a shell command. An adapter
MUST treat `instructions`, `context`, and `adapterOptions` as data. It MUST NOT evaluate their
contents as shell syntax.

An adapter SHOULD exit zero after emitting a valid response. Chalk MUST attempt to parse a complete
response even when the adapter exits non-zero, because an adapter may have normalized a provider
failure before its process exits. If stdout is not one valid response object, Chalk MUST treat the
invocation as an adapter transport failure.

Unknown fields MUST be ignored. A receiver MUST reject an unknown `protocolVersion` with
`status: "unsupported"`; it MUST NOT guess compatibility across major protocol versions.

## 3. Request envelope

| Field | Required | Contract |
|---|---:|---|
| `protocolVersion` | yes | MUST equal `chalk-agent-adapter/1`. |
| `requestId` | yes | Opaque identifier generated by Chalk and echoed by the adapter. |
| `role` | yes | One canonical role from section 7. |
| `instructions` | yes | Provider-neutral role instructions owned by Chalk. |
| `context` | yes | Task or run context for this invocation; MAY be empty. |
| `access` | yes | `read-only` or `workspace-write`. |
| `output` | yes | Expected output contract from section 4. |
| `timeoutMs` | yes | Positive deadline enforced by Chalk; adapters SHOULD also honor it. |
| `workingDirectory` | yes | Absolute directory in which the adapter process is started. |
| `adapterOptions` | no | Opaque JSON object owned by the selected adapter. Chalk MUST NOT interpret provider-specific keys. |

### Access requests

`read-only` means the role MUST NOT create, edit, rename, or delete workspace files and MUST NOT run
commands whose intended effect mutates them. `workspace-write` means the role MAY mutate files
inside the supplied working directory as required by its role. Neither value grants access outside
the surrounding OS sandbox.

An adapter that cannot honor the requested access MUST return `status: "unsupported"` before making
a model call. Provider permission flags are not the sole authority: Chalk SHOULD independently
compare workspace state before and after a `read-only` role and refuse a result that mutated it.

## 4. Output request

`output` MUST contain a `kind`:

- `{ "kind": "text" }` — a successful response MUST contain `text`.
- `{ "kind": "json", "schema": "<role-schema-id>" }` — a successful response MUST contain
  `structured`; Chalk validates that value against the named role contract.
- `{ "kind": "none" }` — success is represented by status and side effects; text is optional.

An adapter MAY use a provider-native structured-output feature. Otherwise it MAY recover JSON from
provider output. In both cases the adapter owns provider decoding, while Chalk owns validation of
the normalized `structured` value against the role schema.

## 5. Response envelope

| Field | Required | Contract |
|---|---:|---|
| `protocolVersion` | yes | MUST equal the request version. |
| `requestId` | yes | MUST equal the request identifier. |
| `status` | yes | `ok`, `failed`, `timeout`, or `unsupported`. |
| `text` | conditional | Required for successful `text` output; MAY contain partial output on failure. |
| `structured` | conditional | Required for successful `json` output. |
| `usage` | no | Normalized non-negative usage fields from section 8. |
| `identity` | no | Opaque execution identity from section 6. |
| `capabilities` | no | What the adapter actually enforced or decoded. |
| `diagnostics` | no | Array of normalized diagnostic objects. |

A diagnostic object SHOULD contain `code`, `message`, and `retryable`; it MAY contain `level` with
`info`, `warning`, or `error`. Diagnostics MUST NOT contain credentials or unredacted secrets.

`status: "ok"` means the adapter completed its role invocation and supplied the requested output.
It does not mean Chalk verification, review, or any other gate passed. Only Chalk decides that.

## 6. Identity and reviewer independence

When known, `identity` has this shape:

```json
{
  "displayName": "adapter-selected model",
  "model": "opaque optional model value",
  "independenceKey": "opaque-comparison-key"
}
```

`independenceKey` is the only field Chalk compares for reviewer independence. Chalk MUST treat it as
an opaque, case-sensitive string and MUST NOT derive or parse it from provider names, model names,
binary names, command flags, or environment-variable conventions. Equal known keys mean correlated
review identity; different known keys mean explicitly distinct identity. If either key is absent,
Chalk MUST report independence as unverified rather than invent an identity.

## 7. Canonical roles

These are all agent-backed stages present when Protocol v1 was defined:

| Role | Existing configuration | Access | Output contract |
|---|---|---|---|
| `executor` | `protocol.executor.command` | `workspace-write` | `text` |
| `planner` | `protocol.planner.command` | `read-only` | `text` (Markdown plan) |
| `reviewer` | `protocol.review.command` | `read-only` | `json`: `chalk/reviewer-result/1` |
| `discovery` | `protocol.discovery.command` | `read-only` | `json`: `chalk/discovery-proposal/1` |
| `feedback` | `protocol.feedback.command` | `read-only` | `json`: `chalk/feedback-result/1` |
| `retro` | `protocol.retro.command` | `read-only` | `json`: `chalk/retro-result/1` |
| `handoff` | `protocol.handoff.command` | `read-only` | `text` |
| `pr-narrative` | `protocol.prbody.command` | `read-only` | `text` |
| `regression-author` | `protocol.regression.authorCommand` | `workspace-write` | `none` |

The structured role contracts preserve the existing top-level shapes:

- `chalk/reviewer-result/1`: `verdict`, `findings`, and optional `decisions`;
- `chalk/discovery-proposal/1`: `tasks` and optional `spec`;
- `chalk/feedback-result/1`: `issues`;
- `chalk/retro-result/1`: `lessons` and `issues`.

Future roles MAY be added without changing the transport version. An adapter that does not support a
role MUST return `unsupported` with a diagnostic naming that role.

## 8. Normalized usage

When the provider exposes usage, an adapter SHOULD report the available non-negative fields:

```json
{
  "inputTokens": 1200,
  "outputTokens": 240,
  "cacheReadTokens": 800,
  "cacheWriteTokens": 0,
  "costUsd": 0.08,
  "turns": 3
}
```

Missing fields mean unavailable, not zero. Chalk MUST NOT fail a role because usage is absent or
malformed; it SHOULD discard invalid usage fields and retain a diagnostic. Adapters own conversion
from provider envelopes into these names. Chalk owns cost-ledger persistence and reporting.

## 9. Lifecycle and failures

Chalk MUST enforce `timeoutMs`. On expiry it SHOULD terminate the adapter, record `timeout`, and
retain bounded stdout/stderr diagnostics. An adapter MAY return `timeout` itself when its provider
reports a deadline first.

For malformed or truncated stdout, Chalk MUST report an adapter transport failure and MUST NOT feed
the partial response into a role parser. For a valid `failed` response, Chalk SHOULD retain `text`
as partial provider output and surface normalized diagnostics. Retry policy belongs to the Chalk
workflow using the role; adapters MUST NOT silently repeat non-idempotent write requests.

Request and response bytes SHOULD be bounded by the Chalk runner. Cancellation SHOULD send the
platform termination signal before a forceful kill. Exact buffer limits and retry counts are Chalk
policy, not adapter behavior.

## 10. Raw-command compatibility

Existing `protocol.*.command` configurations remain a supported compatibility interface. Chalk
normalizes each configured command into an internal `raw-command` profile; users do not have to
rewrite configuration to adopt Agent Runner.

The compatibility adapter MUST preserve the pre-v1 stage behavior:

- it executes the configured shell command in the same working directory;
- it sends the exact stage prompt bytes that the stage received before Agent Runner;
- it preserves live executor output and each role's existing parsing/fallback behavior;
- it preserves timeout and buffer behavior until a separately documented migration changes it; and
- it does not claim an `independenceKey` unless the user explicitly configures one.

During migration an implementation MAY retain historical command-string warnings, but inferred data
MUST NOT be represented as Protocol v1 identity and MUST NOT affect adapter routing. Provider-aware
flag injection and envelope parsing move to real provider adapters; they are not features of the
generic raw-command contract.

## 11. Responsibility split

| Chalk core owns | Adapter owns |
|---|---|
| task state, gates, criteria, and role selection | provider CLI process and provider flags |
| canonical instructions and task/run context | mapping instructions/context to provider prompts |
| requested access and independent read-only mutation detection | provider permission/sandbox mode |
| process deadline, response parsing, role-schema validation | provider streaming/envelope decoding |
| normalized result consumption and cost ledger | usage and identity normalization |
| retry policy, review cadence, and done/merge decisions | provider authentication and model selection |
| legacy configuration normalization | redaction of provider diagnostics |

An adapter MUST NOT edit Chalk spine state, mark a task done, weaken a gate, or decide that acceptance
criteria are satisfied. Chalk core MUST NOT inspect provider names or flags to route behavior.

## 12. Examples

### Text request and response

<!-- example:text-request -->
```json
{
  "protocolVersion": "chalk-agent-adapter/1",
  "requestId": "req-plan-1",
  "role": "planner",
  "instructions": "Produce a concise implementation plan.",
  "context": "Task: add a provider-neutral runner.",
  "access": "read-only",
  "output": { "kind": "text" },
  "timeoutMs": 600000,
  "workingDirectory": "/workspace/project",
  "adapterOptions": {}
}
```

<!-- example:text-response -->
```json
{
  "protocolVersion": "chalk-agent-adapter/1",
  "requestId": "req-plan-1",
  "status": "ok",
  "text": "## Plan\n\n1. Introduce the runner seam.\n2. Migrate the planner.",
  "usage": {
    "inputTokens": 120,
    "outputTokens": 34,
    "turns": 1
  },
  "identity": {
    "displayName": "configured planner",
    "model": "opaque-model-value",
    "independenceKey": "planner-family-a"
  },
  "capabilities": {
    "accessEnforced": "read-only",
    "structuredOutput": "none"
  },
  "diagnostics": []
}
```

### Structured reviewer request and response

<!-- example:json-request -->
```json
{
  "protocolVersion": "chalk-agent-adapter/1",
  "requestId": "req-review-1",
  "role": "reviewer",
  "instructions": "Try to refute the change against every criterion.",
  "context": "Criteria and diff supplied by Chalk.",
  "access": "read-only",
  "output": {
    "kind": "json",
    "schema": "chalk/reviewer-result/1"
  },
  "timeoutMs": 600000,
  "workingDirectory": "/workspace/project"
}
```

<!-- example:json-response -->
```json
{
  "protocolVersion": "chalk-agent-adapter/1",
  "requestId": "req-review-1",
  "status": "ok",
  "structured": {
    "verdict": "pass",
    "findings": [],
    "decisions": []
  },
  "identity": {
    "displayName": "configured reviewer",
    "independenceKey": "review-family-b"
  },
  "diagnostics": []
}
```

### Failure response

<!-- example:failure-response -->
```json
{
  "protocolVersion": "chalk-agent-adapter/1",
  "requestId": "req-review-2",
  "status": "failed",
  "text": "partial provider output",
  "diagnostics": [
    {
      "level": "error",
      "code": "provider-exit",
      "message": "The provider CLI exited before producing a verdict.",
      "retryable": true
    }
  ]
}
```

The standalone [fake Protocol v1 adapter](../examples/agent-adapter-v1/fake-adapter.mjs) implements
this transport using only Node built-ins. It is an executable fixture, not an Agent Runner or a real
provider integration.

Adapter authors can validate an executable with the published offline
[conformance kit](./ADAPTER_CONFORMANCE.md).
